# Docker 部署与依赖安全修复计划

## 目标与边界

- 修复发布镜像中已有修复版本的 Critical/High 依赖漏洞。
- 让 CI 在发布前阻断仍可修复的 Critical/High 漏洞，而不是先推送再报告。
- 完善 Compose 的日志、资源和端口绑定配置，不改变默认业务流程。
- 将现有 `data` 复制到隔离目录进行实际部署；原始 `data` 始终只读，不直接挂载到测试容器。
- 保留用户已有的 `.gitignore` 和 `ddns_sync.py`，不纳入本次修改。

## 阶段一：依赖和运行镜像

**状态：已完成。**

- 前端依赖完成兼容更新；因 `react-router-dom` 当前没有安全版本，改用官方 `react-router 8.3.0`，`npm audit` 为 0。
- `python-multipart` 从 `0.0.22` 升级到 `0.0.30`。
- Go 构建环境升级到 `1.26.5`，`x/crypto`、`x/net`、`x/text` 等模块升级到已修复版本。
- 运行镜像安装 Debian 当前安全更新，移除未使用的 `curl` 及其传递依赖。
- Node 构建环境升级到 `22.22.0-alpine3.23`，Go 构建环境升级到 `1.26.5-alpine3.23`。

## 阶段二：CI 和 Compose

**状态：已完成。**

- 镜像发布改为“本地构建 → Trivy 报告 → 可修复 Critical/High 门禁 → GHCR 推送”。
- 发布工作流仅在版本标签或手动触发时推送，避免同一提交因 `main` 和版本标签重复发布。
- 单架构构建移除不需要的 QEMU，并保留 Buildx GHA 缓存。
- Compose 移除固定容器名，增加可配置监听地址、内存上限、PID 上限和 Docker 日志轮转。
- 中英文部署文档和 `.env.example` 已同步新配置。

## 阶段四：迁移数据实际部署

**状态：已完成。**

- 原始数据迁移前后均为 21 个文件、6,339,441 字节，SHA-256 清单无新增、删除或内容变化。
- 数据只复制到 WSL 隔离目录；容器、数据副本和审计日志已在验收后清理。
- 实际配置校验通过：8 个远程订阅、9 个 YAML、3 个用户、1 个管理员 Token、3 个模板、27 个自定义节点。
- 部署前 9 个 YAML 共 6,288 个节点；所有 YAML 均可解析，4 个实际订阅输出均可生成。
- 8 个定时任务全部恢复，启动时间通过最多 120 秒抖动分散；启动日志没有调度恢复、锁或配置错误。
- 实际“全部更新”结果为 6 成功、2 失败；两项失败均由上游返回 HTTP 403。更换多种常见客户端 User-Agent 后仍失败，说明是上游或服务器出口限制，不是解析或锁问题。
- 两项失败订阅的原 YAML 均保持不变；成功更新中仅一项节点数减少 2 个，没有大规模丢失。
- 更新后 8 个订阅锁全部可以立即重新获取，没有残留锁死。
- 强制重建容器后，健康检查、配置、9 个 YAML、4 个输出、8 个定时任务和 8 个锁再次通过。
- 数据目录属主为 `1000:1000`，目录权限为 `700`，文件权限为 `600`；应用主进程以 `1000:1000` 运行。
- 实际数据空闲资源约为 0.15% CPU、167.1 MiB 内存、11 个 PID；默认 512 MiB/256 PID 限制有足够余量。

## 关键决策和后续注意事项

- 不直接在原始迁移数据上运行容器，避免入口脚本的 `chown`、`chmod`、配置迁移和刷新写入改变原文件。
- CI 只忽略没有修复版本的基础镜像漏洞；一旦供应商发布修复，门禁会自动阻止旧镜像发布。
- 不把本机 Docker 地址池异常写进项目默认配置；隔离验收使用现有 `bridge` 网络。
- 两个 HTTP 403 订阅需要由运营侧处理出口限制，或在面板中配置可用的“订阅代理”；应用已正确保留旧数据并报告部分失败。
